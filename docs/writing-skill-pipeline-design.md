# 写作手册 → 开箱即用写作 Skill：设计与实施计划

- v1 · 2026-09-13 · 基线 commit `0a81c36` (v0.3.15)
- 需求来源：用户实测需求 —— 扫描版《写作手册》(PDF) 上传 → 自动生成 skill；使用时**先判意图→找分类→结合要求+范文写→交审稿人审→多轮迭代→不确定处问用户确认→改到满意**；训练期再加一层**更高级裁判**（先试用 skill，过程+结果都满足要求才放行）。

---

## 0. 需求拆解（原话 → 4 个机制）

| 编号 | 机制 | 一句话 |
|---|---|---|
| **M1** | 摄取 | 扫描版 PDF → 可结构化处理的长文本 |
| **M2** | 训练抽取 | 从手册里抽出：① 通用写作要求 ② 写作分类体系 ③ 每类的具体要求 ④ 每类的**真实范文** → 落成 skill 文件 |
| **M3** | 训练裁判 | skill 生成后**先试用**（拿手册里的已知素材当输入跑一遍），用独立裁判对照手册打分；不达标 → 带裁判意见回炉重生成 |
| **M4** | 使用编排 | 意图分类 → 命中分类 → 注入该类的「要求 + 范文」起草 → 审稿人审 → 多轮迭代 → **需要人拍板的点反问用户** → 满意才交付 |

## 1. 现状盘点（代码级证据，不是猜的）

| 需求 | 现状 | 锚点 |
|---|---|---|
| M1 扫描 PDF → 文本 | ✅ **已通** | 上传落地 `source/*.pdf` → `ocrd`(RapidOCR, 127.0.0.1:8093) `/extract` → `source/<base>.txt`。实测存在 `data/skills/公司新闻通稿/source/real_scan.txt` |
| M2 分类体系 + 各类要求 | ❌ **完全没有**。step1 只抽「风格画像」8 个平铺字段（audience/style/structure/tone/taboo/length/terms），没有"分类"这一维度 | `skillgen/generator.go` `extractAttributes` |
| M2 真实范文切分 | ❌ **现在范文是 LLM 编的**。`buildExamples` 对 write 类直接让模型"生成一篇 400-900 字示例范文"；只有上传文件"像文章且 >500 字"时才复用原文件——整本手册会被当成一篇文章误选 | `generator.go buildExamples` |
| M2 范文进 prompt | ❌ **运行时根本不注入 `examples/`**。`LoadSkill` 只读 system_prompt + template；`Generate` 拼的 sys 只有技能提示词+骨架模板。实测 `公司新闻通稿/system_prompt.md` 中「范文/示例」出现 **0** 次 | `agent.go:377` `agent.go:475` |
| M3 训练裁判 | ❌ 只有一个静态校验：sysPrompt<300 字符、write 类必须有 examples，两条 `if` | `generator.go:156 validate()` |
| M4 审稿人 / 多轮迭代 | ❌ 单轮直出，`Generate` 一次流式输出就 `evDone` | `chat.go:312` |
| M4 不确定 → 问用户 | ⚠️ **机制已存在但只服务于模板填充**：`FillResult.Clarify` → SSE `asked=true` 通道 | `agent.go:765-978`、`chat.go:277-286` |

**结论**：M1 是现成的；M2/M3/M4 是真空，且 M2 的缺口最致命——**分类不存在、范文是编的、真范文还不进 prompt**，所以现在拿手册训出来的写作 skill 只是"一份风格摘要"，而不是"按手册分类、引手册范文的写作系统"。

## 2. 女娲 skill 的可迁移机制（读的是上游 `alchaincyf/nuwa-skill` 原文，非印象）

| 女娲的做法 | 出处 | 迁移到写作场景 |
|---|---|---|
| **答题 / 评分严格分离**：依据 SkillLens 论文（arXiv 2605.23899）实证 **LLM 自评准确率仅 46.4%**，故答题 agent 只读 skill、禁用外网，评分 agent 独立运行、对照一手事实判定 | `examples/*/FIDELITY.md` | 训练裁判必须是**独立调用**（新 context、只给手册原文 + skill 产物），绝不让生成 skill 的那个上下文给自己打分 |
| **加权评分卡**，不是"好不好"：立场 30 / 风格 20 / 边缘诚实 20 / 来源透明 15 / 结构完整 15 = 100 | `FIDELITY.md` | 换维度：**分类判定正确性 / 要求依从性 / 范文对齐度 / 结构完整度 / 无幻觉**（编造手册里没有的规则） |
| **迭代有上限**：Phase 2→4 最多 2 轮，仍不达标就**标注薄弱维度交付最优版本**，不做无限打磨 | `nuwa-SKILL.md:555` | 裁判回炉默认 3 轮上限；超限 → `fidelity.md` 写明薄弱项后放行，不卡死流程 |
| **Agentic Protocol**：skill 内置「问题分类 → 按类型分派研究维度 → 回答」三步，且研究维度必须**从提炼出的框架反推** | `nuwa-SKILL.md:468-513` | 就是用户要的"先判意图→找分类"：路由表 + 分流写进 skill 的 system_prompt，而不是靠外层硬编码 |
| **双 agent 精炼**：A 走结构 8 维评估，B 走"激活触发条件 / 可操作性"评审 | `nuwa-SKILL.md:561-580` | 对应我们的「结构审稿人」+「依从性审稿人」两个视角 |

## 3. 目标架构

### 3.1 新增文件实体（左树会多出这几组，需同步登记 `store/skill_files.go` 的 kind）

```
skills/<slug>/
  system_prompt.md          现有 · 改为内嵌「分类路由规则」
  style_profile.md          现有 · 不可变风格锚（保留）
  categories/               【新】分类体系
    _index.md                 路由表：类别 → 触发特征 → 要求文件 → 范文目录
    01-<类别>.md              该类具体要求（手册原文摘录，不重写）
  examples/<类别>/NN.md      【改】按类别分目录，内容 = 手册原文切分（不再 LLM 编造）
  reviewer.md               【新】审稿清单（两个视角：结构 / 依从性）
  fidelity.md               【新·只读】训练裁判的评分卡结果（每轮一行）
  source/                   现有 · OCR 后的 <name>.txt 在此
```

### 3.2 训练期流水线（现 8 步 → 10 步）

1. 素材摄取（复用 `ocrd`，已是现状）
2. 风格画像抽取（现状 step1，保留）
3. **【新】手册结构抽取**：一次调用输出 JSON `{分类列表[{名称, 触发特征, 要求段落锚点, 范文起止锚点}], 通用要求}`；锚点用"章节标题/首末句原文片段"而非页码（OCR 页码不可靠）
4. **【新】范文切分（纯代码，不过 LLM）**：按锚点把 `source/*.txt` 切到 `examples/<类别>/`；切分失败 → 降级为把整段作为 `reference` 落盘 + 在 `fidelity.md` 记一条 warning，**不硬失败**
5. **【改】生成 `categories/_index.md` + 各类 `<n>-<类别>.md`**（原文摘录 + 从要求里提炼的 checklist）
6. 元数据 / 表单参数（现状 step2）
7. 技能类型判定（现状 step3）
8. **【改】system_prompt 必须包含三步协议**：① 判类别（列出类别+触发特征，不确定时问用户）② 读该类要求 ③ 对齐该类范文结构与篇幅
9. 骨架模板 + 范文索引（现状 step5/6，改掉"编范文"）
10. **【新】裁判循环**：
    - 试用：用 2-3 道题（从手册各分类取素材当输入）跑 draft → 拿到真实产物
    - 判分：独立 context 的裁判，输入 = 手册原文 + skill 产物 + 试用产物，按 5 维评分卡打分
    - 未过线 → 把扣分项与修改建议作为反馈，回到步骤 5/8 重生成（**最多 3 轮**）
    - 全程 SSE 推送：`裁判第1轮: 62/100 未过 · 分类判定错(扣18) 范文错位(扣15)` → 管理员看得见每轮分数
11. 落盘 + 注册（现状 step8）+ 写 `fidelity.md`

### 3.3 使用期三段式（只对 `skill_type=write` **且** 存在 `categories/` 的 skill 生效）

```
① 路由   Eval/EvalTurn 增加 category 字段（一次便宜调用）
         不确定 → 复用 Clarify 通道问用户"是要写通知还是会议纪要？"
② 起草   注入 system_prompt + categories/<命中>.md + examples/<命中>/*.md（首篇全文，其余摘要）
③ 审稿   独立 context 审稿，输出 {verdict, issues[{severity, 违反手册哪条, 建议改法}]}
         ├ blocking 且能自改 → 直接改，把"改了哪几处"给用户看
         ├ blocking 但需人拍板（事实缺失/手册未覆盖的取舍）→ Clarify 反问，答完续跑
         └ 无 blocking → 交付；最多 2 轮，第 3 轮带"仍有 N 处待人工确认"交付
```

SSE trace 帧序（用户要求显性可见）：

```
① 意图分析 → ② 分类判定：会议纪要 → ③ 对齐要求与范文 → ④ 起草(1)
→ ⑤ 审稿轮1：2 处问题 → ⑥ 修订 → ⑦ 审稿轮2：通过 → ⑧ 交付
```

### 3.4 裁判 / 审稿评分卡（两处共用同一套维度）

| 维度 | 权重 | 判据 |
|---|---|---|
| 分类判定正确性 | 25 | 归到手册里最匹配的那一类 |
| 要求依从性 | 25 | 逐条对照该类 checklist，缺一条扣分 |
| 范文对齐度 | 20 | 结构/篇幅/称呼/落款与范文一致 |
| 结构完整度 | 15 | 必备要素齐全、顺序正确 |
| 无幻觉 | 15 | 未编造手册里不存在的规则/格式 |
| **通过线** | **≥80** 且无单维 <15 | |

### 3.5 不动的东西（防回归）

- 非 write 类（docgen / template / query）：走原路径，零改动
- 无 `categories/` 目录的老 skill：`LoadSkill` 不注入任何新东西 → 行为与今天逐字节一致
- 双开关：`skill_type=write` **且** `categories/` 存在，才启用三段式

## 4. 分阶段实施 + 验收（每阶段可独立上线）

### P0 · 打通主链（能用）
1. `categories/` + `examples/<类别>/` 两个新 kind 登记 + 左树显示
2. 训练期：结构抽取 + 范文**原样切分**（干掉"编范文"）
3. 运行时：注入命中类别的「要求 + 范文」
4. 使用期：审稿 1 轮 + trace 显性帧
- **验收断言**（自己跑，不让用户点）：拿真手册建 1 个 skill →
  a. `examples/*/` 下每个文件的内容都能在 `source/*.txt` 里**找到原文**（防幻觉断言）
  b. 3 个不同分类的写作请求 → 路由命中 3 个不同类别（不是全落第一类）
  c. 抓取实际发给模型的 prompt → `grep` 到该类要求与范文片段（现在为 0 命中）
  d. 审稿至少报出 1 处**真实**问题（人工核对判据成立），不是空话
  e. SSE 帧序 = 设计值

### P1 · 训练裁判
5. 裁判循环（独立 context）+ 5 维评分卡 + `fidelity.md` + 3 轮止损
6. 管理端实时显示每轮分数与扣分项
- **验收**：故意注入一个残缺手册（只给"要求"不给范文）→ 裁判必须判**不通过**并在扣分项里点名"范文缺失"；补回范文 → 判通过（**双向自证**，避免假绿）

### P2 · 多轮 + 反问 + 版本
7. 审稿最多 2 轮 + Clarify 反问合并进同一轮（用户答完自动续跑，不用重新发起）
8. 每轮修订与 `versions/` 快照联动（可回滚到任一稿）

## 5. 风险与止损

| 风险 | 止损 |
|---|---|
| 手册没有严格"范文"，只有穿插的示例片段 | 结构抽取允许 `examples: []`；此时裁判「范文对齐度」维度自动不计权（权重归一化），不判失败 |
| OCR 串行/错字导致切分锚点错位 | 锚点用首末句模糊匹配（容忍编辑距离）；匹配失败降级为整篇 reference |
| 裁判循环 token 成本翻 3-5 倍 | 只在 write + categories 双开关下启用；裁判用便宜模型可配置 |
| 审稿人把好稿改坏 | 每轮改动需**逐条对应一个 issue**；纯风格偏好类 issue 只提示不自动改 |
| 老 skill 行为漂移 | 双开关 + 逐字节回归断言（无 categories 时 prompt 拼接结果与今天完全一致） |

## 6. 默认值（用户未反对即照此实施）

| 决策点 | 默认 |
|---|---|
| 范文来源 | **原样切分手册原文**，禁止 LLM 重写（防幻觉，也是本次最关键的修正） |
| 训练裁判轮数上限 | 3 轮，超限带薄弱项交付 |
| 使用期审稿轮数上限 | 2 轮，超限带"待人工确认项"交付 |
| 通过线 | 加权 ≥80 且无单维 <15 |
| 分类数量 | 由手册决定，3-8 类；超过 8 类合并相近项 |
| 反问时机 | 只在「事实缺失 / 手册未覆盖的取舍」时问，风格分歧不打扰用户 |


## 7. 材料侧实测（测试料：50 页扫描版《企业新闻稿写作手册》，2026-09-13 自造）

自造 fixture：`/root/skillforge/testdata/manual/manual-scan.pdf`（50 页 / 35.6MB / 240dpi 灰阶 / 44,202 汉字 /
总则 + 12 类新闻稿（各类含要点与范文）+ 稿件自查清单 25 项 + 送审判定三档）。生成脚本见同目录 `build_manual.py`。

实测结论（决定抽取阶段的设计取舍）：

1. **页眉是最大噪声源**：50 页里 48 页的页眉被 OCR 识别出来，同一行重复出现 48 次，占全部文本行的 4%。
   抽取时必须做**高频重复行过滤**（出现次数 ≥ 页数的 60% 且长度 < 40 字 → 判为页眉页脚丢弃），
   否则 12 类 skill 的"通用要求"里会混进 48 行页眉。
2. **剥掉页眉页脚后内容保真度 0.989**（源 44,202 汉字 vs OCR 43,613 汉字，字符级相似度）；
   不剥离时 0.981。数字类条款全部保住（"22 个字""25 项""3000 万元""18.60""1800 余人"）。
3. **数字丢失是渲染侧问题，不是 OCR 侧问题**：初版小节编号 `1.1` 被识别成 `口口口`，
   根因是标题字体 `DroidSansFallbackFull.ttf` 没有阿拉伯数字字形（`has_glyph('1')==0`，渲染成 notdef 方块），
   OCR 只是忠实读出方块。换 `wqy-zenhei.ttc` 后 `1.4`、`22 个字` 全部正确。
   → 教训：OCR 出方块先查**源渲染字体覆盖**，别急着调 OCR 参数。
4. OCR 侧资源配置：单页约 8-10s（240dpi 密集正文，200dpi 推理）；50 页整体约 9 分钟，
   进程峰值 RSS **1.44GB** —— 见 `skillforge-scan-pdf-ocr` skill 的 OOM 修复记录。
