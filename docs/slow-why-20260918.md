## 三、根因：两条，都在流式层

### R1（主凶）流式客户端没有「读空闲看门狗」
- `internal/llm/stream.go:289`：`streamHTTPClient()` 超时 = **10 分钟**。
- 分类跳在 **6.0s 就把答案流完了**，之后 provider 既不关连接、也不给字节，我们干等到
  600s 客户端超时 → 实测 **616.5s**（= 600s 超时 + 16.5s 重试）才继续。
- **用户说的「一直卡着计时」就是这 610.5 秒。** 不是模型慢，是我们没有「多久没字节就掀桌」的尺子。

### R2 流被截断时不校验「有没有正常结束」
- 半截正文直接丢给 `json.Unmarshal` → 服务端日志：
  ```
  [classify-retry] unmarshal err=unexpected end of JSON input raw_out="{\""
  [classify-retry] unmarshal err=unexpected end of JSON input raw_out="{"
  ```
  （20:38、20:39、20:44 共三条，raw_out 只有 2~3 字节）
- 于是白跑一次 classify-retry：**这一跳的账直接翻倍**。

### F1（次要但显眼）起草跳的材料在 12.0s 断粮
- `chat.go` 只挂了 4 处 `clock.Thinking`（分类跳 / 未命中兜底 / docgen 分支），**起草、审稿、改稿一条都没挂**。
- `internal/agent/progress.go` 里 `contentSink` 就是为这种「关了思考链但 content 在流」的跳准备的，现成没用上。
- 结果：39.8 秒里模型正在逐字吐正文，屏幕上却只有那个跳动的计时器。

---

## 四、修法（按收益排序）

1. **加读空闲看门狗**（stream.go）：无字节超过 ~20s 即 abort，按 transient 重试。
   610s 的卡顿直接压到 20s 量级。同时给分类跳设 hop 级预算（它是「按规则选格子」的活，25s 足够）。
2. **流结束必须校验终止信号**（`[DONE]` / `finish_reason`）：不完整当错误，绝不拿去解析。
   消掉 `raw_out="{\""` 这类白跑的重试。
3. **起草/改稿跳接 `contentSink`**：让 39.8s 那段有字在动（尾部 160 字一路滚），
   这是用户点名要的「中间可以流式输出思考的一些中间材料」。
4. （可选）材料顶到上限后改为滚动更新而非冻结，避免「满 160 字后就一动不动」的观感。

## 六、2026-09-19：账本脚本自己撒谎（本轮最贵的一课）

量「慢在哪一步」用的 `scripts/measure_chat_latency.py`，它解析 trace 帧时写的是：

```python
if isinstance(ev, list):
    ev = ev[0] if ev else {}     # ← 就是这一行
```

trace 帧是**数组**，第 0 位永远是**最早那一步**（① 意图分析，已 done、没有 material），
而「计时器此刻挂在哪一步」和「中间材料」都挂在 **active** 那格上。于是：

- 「各步首次出现时刻」永远只有 ① 意图分析；
- 材料帧被整批看漏 → 「屏幕上有没有东西在动」判成全无变化；
- 真值最大静默 **3.6s** 被报成 **66.3s**。

我拿着这份假账去追「服务端没发材料」，追了一轮才想起去抓原始帧 —— 一抓就露馅：
首材料 0.0s、材料滚到 69.0s。

**尺子撒谎时，指向的永远是别人。** 修法照 2026-09-18 那次（39.8s 假静默）的规矩来：
把挑帧 / 判可见变化 / 算静默抽成 `pick_active_step`、`trace_visible_key`、`top_silences`
三个纯函数，再配一把合成料的确定性尺子
`web/tests/measure_latency_parser_mutation_check.py`（12 条，接进 preflight + CI）。
关键是**每族断言都带对照物**：老实现（取 `steps[0]`）必须在同一份合成料上报出
66.3s 假静默 —— 否则「断言恒真」和「料根本没喂进解析层」长得一模一样，分不出来。

## 八、2026-09-20 复测：那 297.7s 零帧到底是什么

### 修前真链路账本（v2609191706，02:26）

| 轮 | 用时 | 首正文 | 最大静默 | 正文 | 交付物 |
| --- | --- | --- | --- | --- | --- |
| 第1轮 技能写稿 | 353.0s | 347.8s | **297.7s**（8.1s → 305.8s 零帧） | 532 字 | 未出现 |
| 第2轮 整理成 Word | 222.7s | — | 155.5s | 0 字 | **未产出** |

第 2 轮的病因写在同一时刻的 stderr 里，只有一行：

```
[classify] hop=60.0s ttft=-1.00s in=2311(sys=8538 ctx=2124 user=105) out=0
           err=Post "https://api.siliconflow.cn/v1/chat/completions": context deadline exceeded
```

`ttft=-1` 是「整跳一个 token 都没收到」。意图识别被 60s 死线掐死后 `intent`/`action`/`skill`
全空，管线照旧往下走 —— 于是「把上面那篇整理成 Word」被当成通用写作，docgen 根本没跑，
用户看到的是「它不管我上文」。**这不是上下文丢了，是分类跳超时后整条链走错。**

### 三层对照（直连同一 provider、同一模型、只切一个变量）

| 实验 | 结论 |
| --- | --- |
| K0 不带思考参数 | 首片思考 **1.27s**、首片正文 46.35s、总 48.9s |
| K1 三件套关思考（enable_thinking=false + reasoning_effort=none + thinking_budget=512） | 思考片 **0**、总 **4.1s** |
| K2 K1 + chat_template_kwargs.enable_thinking=false | 思考片 0、总 4.5s |
| P1 纯文本 / P2 json_object（都保留思考） | P1 572 字 / 46.4s；P2 正文 **6 字** / 80.8s，思考 2941 片 |
| C1 关思考 + json_object（1.4 万字输入）/ C2 同款纯文本 | 首片正文 1.73s / 1.9s，总 22.1s / 36.3s |

即：**开关是有效的**（K1/K2），**JSON 模式在关思考时不堵**（C1）；P2 的惨状是「开思考 +
json_object 把实质内容挤进思考链」——审稿/改稿那一类跳要留意。
预算重复实测（6 样本）：不限 n=2 → 正文中位 1307 字 / 首片 240s / 总 258s；预算 1024 n=3
→ 正文 904 字 / 首片 25.7s / 总 37s；预算 2048 n=1 → 825 字 / 首片 45.8s。

### 2026-09-20 改判：默认从「不限」翻成 1024（本轮上车）

上面那句「掉质量是真掉（1307 → 904），所以默认不开」**被更硬的线上数据推翻了**。
推翻它的不是又一个探针，是**线上生效档**（provider=siliconflow、model=Qwen/Qwen3.6-27B，
读 `llm_config.is_active` 拿的，不是 env）上同一句「1 万字素材 + 写 1500 字新闻稿」的复测：

| 档位 | 首片正文 | 正文字数 | 总时长 |
| --- | --- | --- | --- |
| 不限 | **226.7s** | 1216 字 | 242.7s |
| 1024（探针档） | 22.76s | 855 字 | 36.3s |
| 1024（复测档） | **26.1s** | **1974 字** | — |
| 2048 | 45.8s | 825 字 | **1909.8s**（退化：正文 256583 字，会撑爆客户端超时） |

三件事因此改了判：

1. **「掉质量」不成立**。1024 两跑是 855 与 1974 字，不限跑是 1216 字 —— 长度落在量测
   噪声里（模型方差），没有一个能被称作「真掉」。1307→904 那次的两侧样本本来就不是同一批。
2. **速度差不在噪声里**。226.7s → 22.8~26.1s 是 8.7 倍，量级差。用户原话「现在速度过于
   慢了…一直卡着计时」就是这 200 秒空转。
3. **「不限」不是安全档**。2048 那行已经证明模型会刹不住车（1909s / 25 万字）。默认不限
   等于把最坏档发给每一个新部署，尤其是离线内网 —— 那边没人会去调 env。

所以默认值从 0（不限）改成 **1024**，并且：
- 要「不限」必须**显式**写 `SKILLFORGE_THINK_BUDGET=0`（不再是默认）；
- **非法值回落 1024**，不许静默变成「不限」（那是把 226 秒又还回去，还查不出来）；
- 守这条的是 `TestStreamChatWritingThinkBudgetDefaultIsBounded` 与
  `TestWriteHopThinkBudgetReachesProvider`（断言钉在真发出去的请求体上）。

⚠️ 这里仍然只有单样本/variance 未知的复测，**没有**做「1024 vs 不限」的多轮统计对照。
按本仓库的规矩，这条结论的强度只到「1024 是更好的默认」，不到「1024 一定更高质量」。


### ⚠️ 必须记账的干扰项

02:37 时 K0 的首片思考是 1.27s，02:40 复跑同一条裸 HTTP 请求 → **读超时（>120s 无字节）**。
同一请求形状在 3 分钟内从 1.27s 退到不响应，说明那段时间 provider 在退化/排队，而我自己
连续几轮压同一个 key 有嫌疑。**所以「353s → 59.5s」不能记成修复的功劳。**

### 修复（0fa5191，v2609200253）与可归因的部分

1. 通用写作路（没命中技能，线上最常见）的执笔走 go-openai SDK：不认预算、没有空闲看门狗，
   而它是最长的一跳 → 改为 `StreamChat + DisableThinking=false`（knobNone，请求体逐字一致）。
2. 构思跳的要点挂在 `contentSink` 上，而它只从 JSON 字符串里抽字（`jsonPreview` 对裸文本
   一个字都不吐）→ 构思要点材料**恒为空**，设计意图被静默吃掉。新增 `rawSink` 并改挂。
3. 新增跳级账本：`[plan]` / `[write-skill]` / `[write-plain]` 各打 hop/ttft/reason/out_pieces。

复测（02:53 部署后，provider 健康）：

```
第1轮 59.5s｜首正文 50.5s｜最大静默 1.3s｜正文 656 字
第2轮 13.7s｜交付物 13.7s ✓
[classify]    hop=2.3s ttft=0.98s intent=write action=write skill=- needs=0
[plan]        hop=3.3s ttft=0.67s reason=0  out_pieces=166 out=262   ← 构思要点在 4.2s 开始滚
[write-plain] hop=53.9s ttft=44.95s reason=2613 out_pieces=351 out=656
[classify]    hop=2.8s ... intent=docgen action=gen skill=办公文档管家 ← 第2轮识别对了，docgen 跑通
```

**可归因的只有两条**：① 构思材料从「0 片」变成「4.2s 起滚动」；② 从此每跳都有账可查。
353s → 59.5s 里有多少是 provider 恢复健康，本账分不开 —— 要分开得在 provider 健康时把
旧二进制（`skillforge.bak-*`）跑一遍同样的两轮。

### 仍留着

- **分类跳超时后静默降级**：60s 到点就丢意图、走错链、不吭声。应改成可识别的失败
  （重试一次 / 按关键词兜底路由 / 至少告诉用户「这轮没识别出意图」），而不是产出错的东西。
- 预算档掉质量（1307 → 904 字），默认不开；要开就按「这批稿子宁可短一点也要快」拍板。
- provider 退化时的体验：看门狗 20s（`SKILLFORGE_STREAM_IDLE_SEC`，0 = 关）会断连接并
  自动重试一次，最差 ~40s 报错 —— 比干等 300s 好，但比正常拿到结果差。
